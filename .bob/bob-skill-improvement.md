*(Skill: kaoto-issue)* **Explicit any lint rules.** ESLint rules like `no-explicit-any` can cause compile-time lint failures when mocking complex third-party types in test suites or rewriting generic step definitions. Suggest that the triage/planning skills proactively remind implementers to use precise type interfaces, type casting, or pre-emptive `@typescript-eslint/no-explicit-any` exception comments at the boundary where `any` is genuinely necessary.

*(Skill: kaoto-issue)* **Ensure test spy assertions are updated with parameter matchers when signature parameters are added or made async.** When core service methods are refactored to take more parameters (e.g. metadata context, path, loaded file maps) or changed to return promises, existing test suites that spy on these methods will fail with assertion mismatches or unhandled rejections if their `toHaveBeenCalledWith` expectation parameters are not updated. Using `expect.anything()` for newly added parameters and stubbing with `Promise.resolve()` is an effective, non-fragile way to update them.

*(Skill: kaoto-issue)* **Change-detection guard is required in settings-update callbacks to prevent infinite or redundant loops.** When onUpdateStepSettings is invoked during state initialization or auto-sync, it can cause redundant or out-of-order calls to `addValidationStep` or `removeValidationStep`. Guarding these calls with an explicit change-detection check (comparing the incoming setting value with `DataMapperValidationStepService.isValidationEnabled(vizNode)`) guarantees that structural YAML changes only fire when the toggle is actually flipped by the user or the schema state.

*(Skill: kaoto-issue)* **Empty document schema definition files can cause non-Primitive documents to fall back to Primitive types.** When stubbing documents in test wrappers (e.g. `DataMapperSettingsModal.test.tsx`), creating a `DocumentInitializationModel` with a non-Primitive target document type but without any dummy definition file contents causes the parser to return error results and fall back to a `PrimitiveDocument` type. This in turn triggers UI-gating logic that hides components (like validation checkboxes). Providing minimal, valid mock schema contents (such as `getShipOrderXsd()`) in `definitionFiles` avoids this fallback.

*(Skill: kaoto-issue)* **XML attribute value escaping in XML Schema wrapper generation.** When generating a dynamic XML Schema wrapper, including unescaped strings in XML attributes (such as ampersands `&` in file paths or target namespaces, e.g., `ext&types.xsd` or `urn:animals&birds`) breaks the XML well-formedness. Implementing an explicit `escapeXmlAttr` helper ensures that any dynamic values used within attributes are correctly escaped (e.g., `&` as `&amp;`), preserving document structure and parsability.

*(Skill: kaoto-issue)* **Avoid over-constraining mocked models with precise catalog types in service unit tests.** When a service test creates lightweight mock models or structures (such as camel ProcessorDefinitions), typing them precisely or constraining helper parameters to narrow generated catalog types can trigger severe TypeScript compilation errors when those types change or differ. Defining mock construction helpers (e.g. `createVizNode(model: any)`) with `any` parameters and using proper `as any` casting for complex nested objects inside assertions guarantees strong test resiliency, simpler code, and zero compilation issues.
